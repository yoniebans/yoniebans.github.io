Overview

Clients, installs & update logistics

A shared scope for the Hermes desktop & update story

The Hermes desktop app is an Electron front end talking to a Python back end. Those two halves can live on the same machine or on different ones — and that single fact fans out into a surprising number of distinct combinations once you add install methods, operating systems, and the meaning of the word "update." This page maps that space so the team is working from one picture.

Why this exists. Not a tutorial and not a design doc — a scoping reference. The goal is agreement on what combinations exist, which are handled today, and which are still open.

Mental model

Two halves, sometimes two machines

Everything below is a consequence of this one split.

The front end

The Electron desktop app — the window you click in. Its UI (the "renderer") is built from web source and, in a packaged install, frozen inside the app bundle.

The back end

The Python agent — the CLI, the gateway, the dashboard server. This is where the model runs and where sessions live. It can be bundled with the desktop app or run on a completely separate host.

When the two halves sit on different machines, they become two independently-updatable things. Most of the complexity on this page traces back to that.
Installs

How Hermes was installed

Five install types — each updates itself differently.

git

The curl / git-clone install. A real checkout on disk. Updates by pulling main and reinstalling.

pip

Installed from PyPI. Updates with pip/uv pip install --upgrade. The fallback when nothing else matches.

homebrew

macOS package manager. Updates via brew upgrade.

nixos

Nix-managed. Not self-applied — the update is owned by the Nix config.

docker

The published container image. Updates by pulling a newer image, not in place.

Sub-variant: uv tool

A pip-family install done via uv tool install lives outside any virtualenv, so it must update with uv tool upgrade rather than uv pip install. Same family, different command.

Running inside a container is deliberately not a signal on its own — both supported container paths stamp their own method, and an unsupported manual install in a container should behave like any off-path install rather than be mistaken for the published image.

Topologies

Where the client points

Four shapes. The last two are where the two-machine problem bites.

Local desktop

Front end and back end on one machine. The app spawns its own bundled back end. One conceptual update loop.

Agent-only (CLI)

No front end at all — just the Python agent. It can be the back end for someone else's remote desktop.

Desktop → remote agent

A thin desktop client over the network to a separate agent host. Two independently-updatable artifacts. This is the core skew case.

Desktop → remote desktop

One desktop's bundled agent acts as the gateway for another desktop. Same skew shape, both ends are full installs.

Update loops

"Update" means two different things

These are separate actions with separate blast radii. Conflating them is the original confusion this scope addresses.

Back-end update

Triggered from the app's update control. It runs the Python agent's own update, routed by install type (git pull, pip upgrade, brew, etc.). It mutates whatever environment the back end runs from — which is why running it against a shared environment is dangerous.

Front-end update

Updating the Electron app itself. The renderer is frozen in the packaged app, so this means shipping a new app build — or, in dev, re-pulling and rebuilding the client source. The in-chat /update command is intentionally blocked in the desktop UI.

The historical trap. In remote mode there were up to four UI surfaces touching "update," with three different behaviours and no labelling of which one meant the client versus the back end. Naming the two loops — and showing each version separately — is the fix.
Reload

Does an in-app update refresh anything live?

Short answer: no. Worth stating plainly because it's easy to assume otherwise.

Python doesn't hot-reload

A long-running back end holds the code it imported at start. After an update writes new code to disk, the running process keeps serving the old code until it's restarted.

No auto-restart

The in-app back-end update updates code on disk and exits. It does not restart the back end and does not reload the front end.

Front end is separate

A back-end update never touches the renderer. In remote thin-client mode the client can only be updated by rebuilding its own source or shipping a new app.

This is precisely why two version indicators are correct: two artifacts, two update loops, neither of which moves the other.
Compatibility

Version vs. compatibility — two different numbers

The displayed version is human-facing. Compatibility is a separate, machine-facing check.

Displayed version

Real semver (e.g. 0.16.0). What the version buttons show. The client shows its own; the back end reports its own. Purely informational.

Compatibility contract

A monotonic integer — a counter that only goes up. Only its ordering matters (higher = newer wire contract), unlike semver where each segment carries meaning. It ticks only when the client⇄back-end protocol changes in a way that matters.

The back end stamps its contract value into each session; the client holds the minimum value it was built against and compares them on connect. They're separated on purpose: semver drifts on every release for reasons that don't affect compatibility, so you don't want to nag on every patch bump — the integer only moves on a genuinely breaking change.

Open gap — the check is one-sided. The guard only fires when the back end is older than the client requires ("back end out of date"). The reverse — a client older than the back end's contract — passes silently. And the one warning that exists points the user at the client-update flow, which is the wrong fix for that direction. Of the three skew states, only one is detected today.

Multiply that by five install types on the back-end side (each with its own update command) and three operating systems (each with its own paths), and the "update" story is genuinely a matrix, not a single flow. The two remote rows are where version skew and the one-sided compatibility check actually matter.

Open

Open questions for the team

Known gaps surfaced while mapping this. None are blockers; all are worth a decision.

One-sided skew check

Should we detect client-behind-backend, and give it its own message + correct fix? Today only back-end-behind is caught.

Worktree mis-detection

A git worktree has a .git file, not a directory, so it mis-detects as pip — and a pip "upgrade" against a git install can silently downgrade. Fix: follow the pointer file.

Stale back end after update

An in-app back-end update doesn't restart the running process, so it keeps serving old code. Surface a "restart required," or restart for them.

Front-end-only install path

No way to install a remote-only desktop client without also bootstrapping a local agent. A real gap for anyone who doesn't want the agent on their machine.
