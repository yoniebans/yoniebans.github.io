# Black-box tests and battery: the storage refactor, before and after the merge

To pin and match database behaviour on main after a refactor of 760 non-test files (+65,172 / -39,576 lines) onto the new persistence stack, we designed black-box tests and a power-user battery.

Compared main before the merge `065f5abbb3` and after it `9dbaa77c4c`.

**The refactor is stable and existing data is intact.** Turn times hold within the limit at the median; opening and paging a session are about 1 ms slower at the median, and a fix for most of that is merged (not re-measured).

*Results at a glance*

### Black-box tests

830 cases in 20 groups

0 broke after the merge

749 and 750 passes before the merge, run 1 and run 2

750 and 747 passes after the merge, run 1 and run 2; the spread is the same four flaky tests that also fail before the merge

### Battery: scripted model

12.1 GB real store copy; 12 scenarios, 96 minutes, 2 runs per tree

0 of 684,892 old rows changed unexpectedly

83 and 83 failed events before and after the merge, two runs each, most planned (a job built to fail, a killed turn)

+0.8 to 1.7 ms open and page, median

### Battery: real models

Claude Haiku / `gpt-5.6-luna`

0 store errors

31 and 32 failed events before and after the merge (pressure stage), none from the store

56 of 56 delegation waves completed

CI's unit and contract suites and lint pass on the six PRs, but none compares the two trees from outside, and the end-to-end lanes are off on pull requests by CI policy.

*Black-box tests*

## No black-box case broke after the merge

We mapped the paths to the database that a code graph and a traced run of the whole test suite could find: 7,056 entry points, then 409 planned tests, then 136 files and 830 cases after the merge. Cases are grouped by the surface a user touches and never call the storage layer, so either tree can be swapped in.

Beyond pass or fail, every case records what Hermes left behind (store dumps, logs, terminal screens, process arguments), and the compare reads those on both trees. During development the tests ran against the refactor and caught behaviour differences that were fixed before the merge (B2).

- **0 of 830 cases broke** after the merge.
- **4 cases vary** between runs: 2 on both trees, 1 only before the merge, 1 only after.
- **79 fail every run on both trees,** so already failing on main before the merge; causes not read.
- **781 of 830 record some difference** in what they left behind. The largest is one expected change (in 726, a set of tables now created on first use instead of at start) plus per-tree folder paths (216 of 216 differing process arguments); row contents differ in 61 cases and logs or screens in more, all grouped, not yet read one by one.

*Battery: scripted model*

## Existing data intact under load; open and page about 1 ms slower

12 power-user scenarios ramp from 2 to 11 at once across six stages (S1 warm-up to S6 cool-down) on a copy of a real 12.1 GB store. A scripted model makes both trees do identical work, so model behaviour cannot cause a difference.

- **Existing data intact:** 0 unexpected changes in 684,892 old rows; integrity checks clean on every run.
- **Failed events level:** 83 per tree over two runs, almost all planned. One was the store refusing a prompt during a 20 s write stall in one after-merge run, traced to the test machine freezing; a forced repro refuses the same hold on both trees.
- **Turn time within the limit:** medians at most x1.14 in any stage.
- **Opening and paging a session are 0.8 to 1.7 ms slower** at the median (x1.15 to x1.37 in S1 to S5); list and search within 13%. A fix for most of it merged on 18 November, [PR #157379](https://github.com/NousResearch/hermes-agent/pull/157379), not re-measured.

*Battery: real models*

## No store errors with real models; every delegation wave completed

Real models exercise what the scripted one cannot: real tool choices and compressions, real 8-wide delegation fan-out (the scripted battery only imitates it), real turn timing. Claude Haiku runs the main loop, Codex `gpt-5.6-luna` the sub-agents. Each tree ran the pressure stage (S3), the 30-minute stage where every interactive scenario runs at once (10 scenarios); one more after-merge run covered all stages.

- **0 store errors** on every run.
- **56 of 56 delegation waves completed,** 448 sub-agent reports (12 waves before the merge, 44 after).
- **Failed events 31 before, 32 after** in the pressure stage, none from the store.
- **Speed within 20%:** read median x1.11, 95th x0.96; turn median x0.94, 95th x1.06; open and page about +0.5 ms.

| Found in a first run | Fixed in the battery |
|---|---|
| Main model asked questions instead of delegating; the account refused the sub-agent model | A direct delegation prompt; a sub-agent model the account accepts |
| Driver waited for a reply marker only the scripted model sends | Take the first bot reply |
| A tool's own database error read as a store error | Tool output left out of the scan |
| Agent log rotated mid-run | Logs kept with backups |

Battery fixes only; no Hermes code changed.

*Conclusion*

## Same behaviour from outside, one small read cost mostly fixed

From outside, main behaves the same after the merge: no black-box case broke, existing data is intact, and failures are level under both batteries. The one cost over the limit, a small slowdown opening and paging a session (list and search slowed within 13%), is mostly fixed by [PR #157379](https://github.com/NousResearch/hermes-agent/pull/157379).
